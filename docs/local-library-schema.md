# Local library schema

## Storage format decision: bounded JSON, not SQLite

**One flat, versioned JSON file** at
`%LOCALAPPDATA%\BruteRuntime\library\index.json`
(`library::default_index_path`), not a SQLite database. This mirrors
every other local store in this project (catalog, calibration, Stage 2
runtime profiles) and is justified by the actual access pattern, not
convention alone:

- Every real lookup the library needs is "by ID," "by hash," or "scan
  every entry" - none of which need a query planner, joins, or indexes
  beyond what a linear scan or a `BTreeMap` grouping (used once, in
  `duplicates::find_duplicate_groups`) already provides.
- Entry counts are expected in the hundreds to low thousands. Measured
  directly up to 10,000 synthetic entries (see
  `docs/stage-3-verification.md` for the real numbers) - every
  operation (save, load, duplicate grouping, storage summary, audit,
  export) stays in the tens-of-milliseconds range even at that scale.
- Introducing `rusqlite`/`sqlx` would add a new dependency, a schema
  migration framework, and background-service-adjacent complexity for a
  problem this scale of data doesn't need solved that way.

If a future stage's access pattern genuinely changes (e.g. tens of
thousands of entries with complex filtered queries), the module
boundary (`library::LibraryStore::load_from`/`save_to`) is the single
seam a storage-engine swap would go through - nothing outside
`library::mod` depends on the JSON representation directly.

## Atomicity and crash safety

`LibraryStore::save_to` writes to `index.json.tmp` first, then
`std::fs::rename`s it over `index.json`. A rename within the same
filesystem is atomic at the OS level - a crash mid-write leaves either
the old complete file or a stray `.tmp` file, never a half-written
`index.json`. Verified:
`library::tests::atomic_write_leaves_no_tmp_file_behind_on_success`.

A missing index file is not an error - `load_from` returns an empty
`LibraryStore` (schema version stamped to current), since "nothing has
been imported yet" is a normal starting state, not a failure. A
genuinely corrupted (malformed JSON) index is a clear, distinct
`LibraryError::Parse`, never silently discarded or partially trusted -
verified: `library::tests::corrupted_index_json_is_a_clear_parse_error_not_a_panic`.

## Schema versioning and migration

`LIBRARY_SCHEMA_VERSION = "stage3-library-v1"` is stamped on the store
and on every individual entry. `LibraryStore::load_from` always calls
`migrate()` after parsing - today a no-op identity transform (this is
the only schema version that has ever shipped), but structured so a
real future migration only needs to add a match arm, not restructure
the load path. Verified with a synthetic older-version fixture:
`library::tests::migrating_an_unknown_older_schema_version_is_a_no_op_today`,
`loading_an_older_schema_version_from_disk_migrates_on_load`.

## `LibraryEntry` fields

| Field | Meaning |
|---|---|
| `library_id` | Random, non-identifying local label (`identity::generate_random_id`, prefixed `model-`) |
| `schema_version` | Per-entry schema stamp |
| `sha256`, `file_size_bytes`, `gguf_version`, `tensor_count`, `kv_count` | Authoritative artifact identity + GGUF structure - see `docs/model-identity.md` |
| `architecture`, `quantization`, `parameter_count` | GGUF metadata, `None` when genuinely unknown (never guessed) |
| `current_path` | Real local path - private state only, redacted on export |
| `original_import_path` | The path first used to import this artifact (kept even after a later `locate` rebinds `current_path`) |
| `imported_at_rfc3339`, `last_verified_at_rfc3339`, `file_modified_at_rfc3339` | Timestamps |
| `file_status` | `FileStatus` - see `docs/model-file-change-detection.md` |
| `trust` | `TrustStatus` - see `docs/trust-and-provenance.md` |
| `last_verification` | The most recent full `GgufVerification` result, or `None` if never verified |
| `catalog_match` | `CatalogMatchResult` - catalog ID + confidence tier + notes |
| `alias`, `notes` | User-supplied text, local metadata only |
| `quarantine` | `Some(QuarantineInfo)` while held back - see `docs/quarantine-and-recovery.md` |
| `managed_copy` | Always `false` today - see `docs/model-import-and-verification.md` |

**Deliberately absent**: `associated_runtime_profile_ids` and
`associated_calibration_record_ids`. See
`docs/runtime-profile-association.md` for why these are computed live
instead of persisted - a persisted list would be a second source of
truth that could silently drift from the actual profile/calibration
stores.

No field ever holds a hardware serial number or other personal
identifier - `library_id` is exactly as non-identifying as Stage 2's
`local_instance_id`, generated by the same mechanism.
